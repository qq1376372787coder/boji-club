| 能力 | 实际结论 |

## 缺陷清单（32 项）

分级：P1 为应阻断本轮完整上线/验收的功能或数据安全问题；P2 为状态展示、运维或体验一致性问题。分级不表示默认关闭开关时每项都已影响生产。合计 P1 28 项、P2 4 项。相关项分别保留，因为修复其中一处不会自动修复另一处。

### AS-01 · P1 · 撤销操作使分片历史脱离权威读取路径

- 位置：`account-server/public/ai-router.php:280,296；business-state.php:14,33`。
- 证据：运行复现 partitioned_undo：撤销前 _partitioned=2，撤销后标记消失；60 天前的分片仍在库中，但新整包只包含本次窗口。
- 影响：历史并非当场物理删除，但权威读取会漏掉窗口外数据，后续同步有继续覆盖风险。必须先修。
- 修复方向：从原始 stateRow 保存 partitioned 布尔值；撤销沿用与正向命令相同的分片写入路径，验证窗口外记录与 AI 历史不变。

### AS-02 · P1 · 撤销较早体重记录会抹掉之后的新测量

- 位置：`account-server/public/ai-router.php:282；commands.php:392`。
- 证据：运行复现 undo_old_weight_removes_newer_weight：先记 70.5，再记 71，撤销第一笔后最终 bodyWeight=null。
- 影响：撤销不是针对测量实体的逆操作，而是回填旧快照；没有检查当前实体是否已被后续操作修改。
- 修复方向：建立 measurement ID 与版本；只撤销目标实体，或要求当前版本匹配并返回冲突。

### AS-03 · P1 · 模型白名单包含高影响确认能力，可绕过独立用户确认

- 位置：`account-server/public/capability-registry.php:143,394；ai-router.php:239；BojiClub/ClubCoachView.swift:241`。
- 证据：运行复现 model_can_commit_schedule_without_user_confirm：仅调用 preview 再由路由调用 schedule.commit_change，安排已移动，actor=ai；没有经过原生确认按钮。
- 影响：needs_confirmation 只是元数据；直接路由未执行该策略。提示词让模型等待确认不能替代服务端权限门槛。
- 修复方向：从模型工具白名单移除 commit/activate 等确认能力；用户确认用独立接口和服务端可核验的交互凭据。

### AS-04 · P1 · 能力写入绑定消息视图生命周期，存在漏执行和重放

- 位置：`BojiClub/ClubCoachView.swift:236,386,441`。
- 证据：源码：.task(id: job.id) 在 pending 消息已有但 result 为空时立即退出；结果完成后 job.id 未变，不会因结果变化自动重跑。路由结果仅存在 View 的 @State，重新进入已完成历史又会请求 resolve。
- 影响：新回复可能不执行能力，重开历史却执行旧请求；异步任务每次都生成新 ID，尤其无法防止重复受理。此项是视图/状态管理源码结论，未跑新 UI 视频。
- 修复方向：把行动交给持久化的消息/行动协调器，以 message_id/call_id 去重；状态恢复只查执行结果，浏览历史不自动重新发写请求。

### AS-05 · P1 · 换肌群和启用计划确认使用未赋值变量，必然拒绝

- 位置：`account-server/public/commands.php:423,469,521`。
- 证据：运行复现 swap_confirm / activation_confirm：Undefined variable $proposalKind，均返回 400“提案类型与命令不匹配”。变量在两个分支之后才赋值。
- 影响：Phase 3 两个主功能即使已有合法服务端提案，也无法确认落地。
- 修复方向：把 proposalKind/proposalPayload 初始化移到分派之前，并增加真实提案创建→确认集成用例。

### AS-06 · P1 · 三个训练能力缺少命令映射；记组契约还会把完成组当未完成

- 位置：`account-server/public/capability-registry.php:64–115；ai-router.php:230；training-commands.php:100,128`。
- 证据：运行复现 training.start_session / finish_session / log_set 均 409“暂不支持直接执行”。三条注册没有 command_type。补充契约探针：log_set 合法输入归一化 completed=false，加入 completed=true 却被注册表拒绝。
- 影响：开始、结束和记组虽在能力列表中，正常 AI 路由无法工作；只补映射仍不能正确记下完成组。
- 修复方向：补全命令映射、真实活动实体解析及完成语义；结束训练增加未保存输入/异常队列确认条件。

### AS-07 · P1 · 异步生成计划只插入映射表，没有真正入后台任务队列

- 位置：`account-server/public/ai-router.php:396–414；weekly.php:233–235`。
- 证据：运行复现 async_only_job_mapping 返回 accepted；函数仅 INSERT ai_user_jobs，没有保存 goal/request、调用 aiProxy 或写 Worker 队列。现有正式提交路径在 weekly.php 会调用 aiProxy。
- 影响：用户看到“处理中”，实际不会从该路径生成候选计划；状态查询只能一直 running。重试/重开历史还会增加空任务。
- 修复方向：复用完整任务提交服务，持久化输入、幂等任务 ID、派发与失败状态；受理成功必须对应可恢复的真实队列项。

### AS-08 · P1 · 启用计划的工具输入与提案输入互不兼容

- 位置：`account-server/public/capability-registry.php:183–204；ai-proposals.php:129–149；ai-router.php:358`。
- 证据：运行复现 activation_router_contract：注册表允许的仅 draft_id；提案必需 sessions，路由又不按 draft_id 加载草稿，返回“提案载荷未通过校验”。
- 影响：即使修好确认变量，正常 AI 启用计划仍到不了预览；简单给输入加 sessions 又会被顶层白名单拒绝。
- 修复方向：服务端按用户和 draft_id 读取可信草稿并生成绑定版本的 diff；不能让模型自造待启用内容。

### AS-09 · P1 · 饮食直存工具没有提供业务层必需的 entry_id 契约

- 位置：`account-server/public/capability-registry.php:226–245；training-commands.php:169–172`。
- 证据：运行复现 nutrition_router_missing_entry_id：符合公开工具说明的 date/meals{name,category,calories} 返回 400。业务层强制每餐 entry_id，但 items schema 只有 object。
- 影响：正常模型调用很容易失败；若让模型随意造 entry_id，又无法保证同一操作重试与真实第二顿饭的区分。
- 修复方向：由可信行动层生成并保存稳定 entry ID，把操作身份传递到命令服务；完善食物项的严格 schema。

### AS-10 · P1 · 饮食与体重降级预览的卡片协议接不上客户端

### AS-11 · P1 · 高影响预览只显示通用句子，用户看不到具体变更

### AS-12 · P1 · iOS 手动体重命令未携带服务端必需幂等键

- 位置：`BojiClub/ClubProposalSync.swift:351–361,366；BojiClub/AppStore.swift:2376；account-server/public/commands.php:89–94`。
- 证据：源码：bodyWeightPayload 只写数值、日期与时间；队列虽计算 identity.key，却仅使用 identity.command。服务端明确要求 64 位 idempotency_key。
- 影响：direct_records 开启后这条原生命令每次都会 400，客户端又把非 409 错误归为 deferred；看似本地保存，实际可能走旧同步兜底。
- 修复方向：把稳定幂等键随命令载荷发送；4xx 参数错误应作为可见终态处理，不能无提示地无限重试。

### AS-13 · P1 · 刷新队列时会删除等待期间新加入的命令

- 位置：`BojiClub/AppStore.swift:2294–2331`。
- 证据：提取原函数进行 Swift 受控异步复现：A 发送期间入队 B，A 成功后队列变为 []，B 消失。for 使用旧数组快照，结束却整体覆盖当前队列。
- 影响：训练或体重在后台同步等待时新增的命令可能丢失，无法再靠稳定 commandId 重放。
- 修复方向：以 commandID 原子确认/删除已处理项；保留执行期间新增项，并在账号/generation 未变时提交队列更新。

### AS-14 · P1 · 队列重试次数不落盘，达到上限反而删掉仍称已保留的操作

- 位置：`BojiClub/AppStore.swift:2299–2331`。
- 证据：提取原函数复现：连续 3 次 deferred 后 attempts=0、persist=0；从 attempts=5 重试后剩余命令 0，却提示“已保留在本机”。只用数量变化判断内容变化，且 >=6 分支没有 append。
- 影响：持久重试状态失真；达到上限或取消时未处理尾项也可能被整体覆盖清掉。
- 修复方向：按条目内容保存更新；保留 failed/deferred 队列和人工重试入口；取消应保留全部未处理项，不以数量判定变化。

### AS-15 · P1 · 执行状态查询和错误恢复协议不一致

- 位置：`account-server/public/index.php:442–445；ai-router.php:197–221；BojiClub/ClubProposalSync.swift:27–76；ClubCoachView.swift:273,321`。
- 证据：服务端查询返回 succeeded/running/awaiting_confirmation，iOS 完成判断只认 completed；查询数据不含 execution_id，替换整条结果后丢失再次查询入口。Swift 解码探针确认 succeeded 不被识别为完成。resolve 的 HTTP/解码错误还直接返回空数组并缓存。
- 影响：成功可能显示未完成，running 查询一次后按钮消失；响应丢失没有可靠 verifying_result 闭环，批次部分成功更难恢复。
- 修复方向：建立统一状态 DTO 与 ID，合并更新而非替换身份；持久化执行标识；网络不确定时查状态，失败不能静默转成空结果。

### AS-16 · P1 · 同一天多次真实称重没有保存为多笔测量

### AS-31 · P1 · “全阶段默认关闭、删新表列即可回滚”的承诺不成立

- 修复方向：分阶段发布代码与兼容 schema，回滚保留扩展列/表；新增路由和消费者使用独立熔断与可验证的降级策略。

### AS-32 · P2 · 提案过期时间不是客户端约定的带时区 ISO 格式

- 影响：过期预览仍可点，时间显示有歧义；服务端确认扫过期仍有保护，因此本项是客户端状态/时区缺陷，不声称已绕过服务端 TTL。
- 修复方向：统一 UTC ISO8601（含 Z/offset）与服务器时间；解析失败应安全降级，并按用户时区显示。
