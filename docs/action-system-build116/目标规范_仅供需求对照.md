# BOJI CLUB V2.0 — AI Action System 通用业务联动架构 V1.0

> 定位：可交给编程 Agent 审计和实施的目标规格；尚未读取现有 BOJI CLUB 仓库，不代表现有数据库、API 或模块已经具备文中结构。
> 目标：用户通过 Club AI 提问、建议、训练开始/结束、改期、换肌群、饮食与体重记录、重生成计划等意图，均由同一套可验证的业务能力体系执行，杜绝 AI 直接修改多个页面或数据表。

## 1. 产品原则与硬性约束

1. **AI 理解，不直接落库**：LLM 只提交结构化能力调用请求；权威业务变更由对应 Domain Service 实现。
2. **相同操作多入口、单一执行服务**：AI 对话、训练页、侧边栏、快捷按钮、系统快捷指令统一调用相同 Command API。
3. **分类执行**：只读查询可直接执行；健康/疲劳问题属于建议，不能顺手改计划；低风险明确数字记录允许按用户设置直存并提供撤销；改期、替换计划等高影响操作必须预览确认。
4. **业务幂等、并发安全**：客户端幂等键 + 提案状态 CAS + 聚合版本号 + 业务唯一约束；事件消费者允许重复投递并去重。
5. **历史不可伪造**：计划安排与实际训练记录分离；变更计划不会改变真实已完成的组数、重量、饮食历史和徽章发放事实。
6. **核心功能离线可用**：训练计时和组数保存不可阻塞于 AI；离线队列及同步冲突可见可处理。
7. **隐私最小化**：按用户授权及用途获取数据；HealthKit 来源、删除及重复同步要可追踪。

## 2. 用户意图 → 能力注册表 (Capability Registry)

不要为具体中文句式硬编码业务逻辑。每个能力包括：`name`, `version`, `description`, `input_schema`, `permissions`, `risk_level`, `needs_confirmation`, `preconditions`, `domain_owner`, `output_schema`, `ui_card_type`, `timeout`, `idempotency_policy`, `audit_policy`。由服务端注册表提供候选工具，模型只能调用白名单。

| 能力 | 场景 | 业务归属 | 副作用与确认 |
|---|---|---|---|
| `training.get_today` | 今天练什么 | Training Read | 只读，直接 |
| `training.get_history` | 上次卧推多少 | Training Read | 只读，直接 |
| `training.start_session` | 开始训练 | Training | 建立或恢复会话；一般直接，防双开 |
| `training.finish_session` | 结束训练 | Training | 会话关闭；未完成记录或异常则确认 |
| `training.log_set` | 刚做了12次 | Training | 明确动作、组数、重量后快速保存 |
| `schedule.preview_change` | 周四休息，周六练 | Schedule | 预览，无副作用 |
| `schedule.commit_change` | 确认改期 | Schedule | 必须基于有效提案与版本执行 |
| `plan.preview_exercise_swap` | 周五练背不练胸 | Plan/Schedule | 必须区分一次性和长期变更 |
| `plan.generate_draft` | 重新生成计划 | Plan + AI | 创建候选新版本，不启用 |
| `plan.activate_version` | 启用新计划 | Plan | 版本切换，必须确认 |
| `nutrition.create_draft` | 拍照/文字记录饮食 | Nutrition | 只生成草稿 |
| `nutrition.save_entry` | 确认这顿饭 | Nutrition | 保存已确认记录，必要时确认 |
| `body.record_weight` | 我今天70.5kg | Body | 可直接记入，支持撤销及去重 |
| `coach.assess_readiness` | 我有点累练不练 | Advisory | 只给建议，不能修改训练安排 |
| `club.get_progress` | 徽章差多少 | Club | 只读 |

建议额外支持 `create_plan_from_goal`、`nutrition.update_entry`、`body.get_trends`、`schedule.get_conflicts`、`training.pause_session`、`training.resume_session`、`action.get_status`、`action.undo` 等标准能力。能力总量应以真实现有业务为准，不要一次性开几十个未经测试的工具。

## 3. 统一行动生命周期 (Action Lifecycle)

### 3.1 状态机

`RECEIVED → INTERPRETED → RESOLVING_CONTEXT → {NEEDS_CLARIFICATION | PREVIEW_READY | EXECUTING_DIRECTLY}`

`PREVIEW_READY → AWAITING_CONFIRMATION → COMMITTING → COMMITTED`

异常与终止：`REJECTED`, `CONFLICTED`, `EXPIRED`, `CANCELLED`, `FAILED_RETRYABLE`, `FAILED_FINAL`。异步计划生成可有 `RUNNING / DRAFT_READY` 状态，但不要把「生成草稿」与「启用计划」合成一步。

状态转换发生在服务端；消息正文只是解释，不能充当操作状态来源。所有状态变化需记录时间、操作者、关联实体与版本。

### 3.2 通用请求结构（示意）

```json
{
  "conversation_id": "conv_123",
  "message_id": "msg_456",
  "capability": "schedule.preview_change",
  "intent": {
    "source_date_local": "2026-10-29",
    "target_date_local": "2026-10-31",
    "scope": "single_occurrence",
    "rest_on_source": true
  },
  "timezone": "Asia/Shanghai",
  "client_context": {
    "active_workout_session_id": null
  }
}
```

注意：`user_id` 只从鉴权上下文取得，忽略模型传入的用户 ID。所有日期由服务端按用户时区及当前时间解析；不明确的「周四」应询问具体周次。

### 3.3 操作提案（Action Proposal）

```json
{
  "proposal_id": "prop_01",
  "capability": "schedule.commit_change",
  "subject_ids": ["occ_29", "occ_31"],
  "expected_versions": {"schedule_2026W44": 12},
  "changes": [
    {"type": "set_rest", "date": "2026-10-29"},
    {"type": "move_occurrence", "occurrence_id": "occ_29", "to_date": "2026-10-31"}
  ],
  "warnings": [],
  "expires_at": "2026-10-24T03:15:00Z",
  "status": "AWAITING_CONFIRMATION"
}
```

提案与原始业务版本绑定，内容不可在确认后被模型偷偷替换。确认由明确的用户交互发起，服务端检查提案属于当前用户、未过期、未取消、还未执行，并重新验证业务前置条件。

## 4. 按业务聚合组织数据：分清模板、安排和事实

- `workout_plan`：训练计划身份、所有者、目标。
- `workout_plan_version`：不可变的计划版本、结构化动作及训练日模板；激活版本单独记录。
- `workout_occurrence`：某一具体日期计划训练什么的实例，包含稳定 ID、状态、关联计划版本和版本号。
- `schedule_exception`：临时休息、改期或单次调整；保持「一次性修改」不污染循环模板。
- `workout_session`：真实开始/结束的训练会话，`active` 状态约束；建议记录来自哪个 occurrence 和当时的计划快照。
- `workout_set_log`：动作、组次、重量、单位、完成时间、修改来源。
- `meal_draft` / `meal_entry`：草稿和正式记录隔离，保存食物量、单位、营养估算来源、图像识别置信信息。
- `body_measurement`：体重数值、单位、测量时间、来源与外部样本 ID；同日允许多次测量，不用简单按日期唯一去重。
- `action_proposal` / `action_execution`：提案、确认、执行和审计记录。
- `idempotency_record`：以 `(user_id, operation_scope, idempotency_key)` 唯一；保留请求摘要、执行状态和已提交结果。
- `outbox_event` / `processed_event`：事件可靠投递和消费者去重。
- `schedule_revision` 或聚合 `version`：用于并发控制和客户端增量同步。

**不变式**：
- 同一用户不得因重复点击创建多个相同进行中的训练；需要数据库层保证（实际可采用约束/锁及强制业务判定）。
- 修改未执行的计划任务，不得把既有已完成 workout_session 迁移、删除或自动改写。
- 不能让两个互斥 occurrence 在同一时间窗口静默覆盖。
- 任何影响付费权益或实物奖励的操作，交给会员或俱乐部确定性规则与审计，不由大模型决定。

## 5. 主要场景的处理策略

### 5.1 「开始训练」

1. 服务端先查询当前用户是否已有 `IN_PROGRESS` 会话；若有则返回 `RESUME_SESSION`，不新建。
2. 若无会话，查当天训练任务或用户明确指定计划。
3. 不明确时返回训练选择卡片；明确时执行 `start_session`。
4. 同一客户端请求使用同一幂等键重试；不同设备同时点也依靠数据库约束/锁避免双开。
5. 训练页以本地持久化方式保存每组与计时状态；离线进入的会话和服务器会话需要约定同步合并策略。

### 5.2 「结束训练」

1. 查活动会话和未提交组数。
2. 有未保存的输入或异常离线队列，则展示「保存并结束 / 继续训练 / 放弃草稿」明确选择。
3. 事务内变更 `IN_PROGRESS→FINISHED`、记录训练摘要与事件。
4. 重复 `finish_session` 返回原完成结果，不二次生成新的训练完成事实、奖励或通知。
5. AI 训练复盘走异步任务，不能阻塞结束操作。

### 5.3 「周四休息，周六练」

1. 解析用户时区、具体周次、源 occurrence。
2. 查周六是否有原训练、休息或冲突；检查未来间隔与目标周期。
3. 生成一次性 schedule diff；只有用户确认后写入。
4. 若周六已有训练，不擅自覆盖：展示顺延/选新日期/取消等有效选项。
5. 修改训练日历的权威 occurrence/exception，提醒与 AI 洞察从事件更新。

### 5.4 「周五不练胸了，我练背」

区分：
- 只改变这个周五：修改单次 occurrence，计划模板不变。
- 以后所有周五都改：创建新 plan_version，展示对未来周期影响后启用。
- 如果用户已开始或完成周五胸部训练：不能篡改已发生历史；可调整剩余会话或未来计划，但需要额外明确规则。

### 5.5 「记录饮食」

- 自然语言明确食物、份量、餐次，可直接生成已填好的草稿并提供保存；高可信、用户明确授权情况下可配置快速直存。
- 图片识别需 `draft → review → commit`，不确定份量需标注为估算且可编辑。
- 创建动作以 `meal_entry_id`/`operation_id` 防止重复保存；重复「再保存一下」应返回原记录而非新增一餐。
- 常吃食物、餐次、最近食物等从结构化数据读取，减少模型调用。

### 5.6 「今天体重70.5kg」

- 解析量纲和测量日期；无单位时以用户明确设置为准，不凭模型擅猜。
- 若同一句在同一对话被重复传输，沿用同一操作幂等键；如果用户确实再次称重，应允许新的测量记录。
- 展示已记录与撤销入口；HealthKit 写入须单独获得授权，设置样本来源标记，避免同步回流造成重复。
- HealthKit 增量同步需处理新样本、删除样本及 anchor，并按来源 ID 追踪。

### 5.7 「周六有点累，练还是不练？」

- **默认只读**：分析近几日训练负荷、休息、用户主观疲劳，以及取得授权并同步完成的睡眠等数据。
- 不够信息先询问疼痛、疲劳严重度或是否有异常症状；不给出伪精确的恢复分数。
- 返回 `AdviceCard`：「休息 / 减量 / 正常训练的选择与理由」，但不修改日历。
- 用户明确说「把周六改成休息」时，再走变更提案与确认。
- 出现明显急性危险症状时按健康安全规则提示寻求医疗评估，不能让 AI 替代医生。

### 5.8 「重新生成训练计划」

1. 查询当前训练目标、器械、可用天数、经验、近期表现和已确认偏好。
2. 生成候选 `plan_draft`，所有动作必须来自可信动作库、数值符合校验规则。
3. 返回新版与旧版的具体对比：周期、频率、肌群、训练量、动作、预计时长及未来已安排任务的处理方式。
4. 允许用户编辑、继续修改、保存草稿；明确确认后创建不可变 plan_version 并切换激活版本。
5. 保留旧版和已完成历史，约定生效时间，不擅自移动进行中的训练或既有训练记录。
6. 对未来 occurrence 的重建在权威事务或有状态的可补偿工作流中执行，变更必须可追踪可恢复。

### 5.9 「开始今天的背部训练，并且把今天午饭记成鸡胸肉」

这属于复合任务，不应当一次模型输出直接执行两个无关领域的写入。编排器拆为 `start_session` 和 `nutrition.create_draft`，分别验证与提交，返回部分成功状态。跨业务模块不能假装拥有一个不存在的全局 ACID 事务。

## 6. 统一接口（仅设计契约，端点可适配现有路由）

```http
POST /v2/ai/messages
POST /v2/actions/resolve
POST /v2/actions/proposals
GET  /v2/actions/proposals/{proposal_id}
POST /v2/actions/proposals/{proposal_id}/confirm
POST /v2/actions/proposals/{proposal_id}/cancel
GET  /v2/actions/executions/{execution_id}
POST /v2/training/sessions/start
POST /v2/training/sessions/{id}/finish
POST /v2/nutrition/drafts
POST /v2/nutrition/entries
POST /v2/body/measurements
GET  /v2/sync/changes?since=revision-token
```

- `POST` 写操作使用 `Idempotency-Key`；身份从服务端登录态获取。
- 读写返回具体领域 ID、版本号、状态、`execution_id`、最新权威数据或刷新指令。
- `409 CONFLICT`：当前版本变化，返回新快照并让用户重新预览；不能静默覆盖。
- `422 UNPROCESSABLE_ENTITY`：参数合法但业务约束不满足。
- `202 ACCEPTED`：仅表明异步处理中；不等于业务已完成。
- 超时先按 execution 或幂等键查询状态；不要自动换键重复执行。

### 确认接口（示意）

```http
POST /v2/actions/proposals/prop_01/confirm
Authorization: Bearer <token>
Idempotency-Key: deviceX-confirm-prop01
Content-Type: application/json

{"expected_proposal_version": 1}
```

服务端对用户身份、提案状态、过期时间、签名/摘要及目标版本做检查，再进行域级事务写入。

## 7. 幂等与并发的参考事务伪代码

```text
BEGIN TRANSACTION
  authenticate user from server session
  INSERT idempotency_record(user, scope, key, request_hash, RUNNING)
      ON CONFLICT -> lock existing row and compare request hash
      if COMMITTED + same hash: return stored result
      if different hash: reject key reuse

  SELECT proposal WHERE owner=user FOR UPDATE
  require proposal.status == AWAITING_CONFIRMATION and not expired
  SELECT schedule_aggregate WHERE id=... FOR UPDATE
  require aggregate.version == proposal.expected_version
  validate business invariants and conflicts again
  apply domain mutations once
  UPDATE proposal -> COMMITTED
  UPDATE schedule_aggregate version += 1
  INSERT outbox_event(event_id, aggregate_id, aggregate_version, payload)
  UPDATE idempotency_record -> COMMITTED, store result
COMMIT
return success + authoritative revision
```

生产实现应妥善处理并发插入等待、失效提案、数据库锁/隔离级别、请求摘要、提交后响应丢失等情况；唯一约束和事务是最终防线。若操作超过单事务能力，采用有状态 Saga/Process Manager + 可补偿步骤，绝不对外谎称原子性。

## 8. 事件与跨模块一致性

事件名称建议：
- `WorkoutSessionStarted.v1`
- `WorkoutSessionFinished.v1`
- `WorkoutSetLogged.v1`
- `WorkoutOccurrenceRescheduled.v1`
- `WorkoutOccurrenceChanged.v1`
- `TrainingPlanActivated.v1`
- `MealEntryCreated.v1`
- `BodyMeasurementRecorded.v1`
- `UserPreferenceUpdated.v1`

`outbox_event` 与业务写入在同一数据库事务内保存，发布进程异步投递。消费者以 `(consumer_name, event_id)` 唯一去重，按聚合版本处理重复和乱序。通知、周报、AI 洞察、俱乐部派生统计从事件更新；权威训练日历应直接读取 Schedule Domain 状态，而不是依赖消息最终同步。若异步投影落后，UI 给出同步状态与重试机制。

**不承诺**“所有模块同一毫秒刷新”；承诺权威数据一致、关键操作立即读到正确值、投影最终可对账收敛。

## 9. iOS 原生交互与全局同步

- 首页 AI 对话只承担意图与结果展示；确认卡片通过 `action_id/proposal_id` 绑定服务器状态，不依赖聊天文案。
- 训练页、日历页、记录页从共享 Repository/Store 获取领域数据；可以使用 SwiftUI `@Observable` 等适合当前最低部署系统的状态管理方案。
- 执行成功后先应用服务器确认的权威 patch/revision，并失效相关 Query Cache；后台刷新其他依赖数据。
- 从任意入口返回时保留训练 session 与对话滚动位置。
- App 回到前台、从推送跳转、切换账户或检测 revision gap 时做增量同步；实时通知（SSE/WebSocket/APNs）只是加速触发，不是唯一数据正确性来源。
- 核心训练记录先持久化至本地数据库，离线队列使用稳定本地操作 ID，并按实体版本与冲突策略同步。
- 网络断开、AI 超时不影响训练计时和本地记录。

### 卡片状态（必须可访问、可恢复）

`thinking → needs_input → preview_ready → confirming → verifying_result → completed / conflicted / failed`

- 对于 `verifying_result`，不要显示“失败，请再点一次”，应查 execution 状态。
- 过时预览必须显示「计划已变化，重新预览」。
- 一旦用户确认，按钮临时禁用只是 UX，真实幂等由服务端保障。
- 允许从 AI 聊天打开对应训练/日历/记录详情页，再返回对话。

## 10. 权限、AI 安全与多模型

- 模型工具调用接口使用严格 Schema/参数校验；若模型支持 strict structured output 则开启，但绝不将 Schema 合规当作业务安全。
- 读取用户数据必须从用户鉴权上下文授权；多租户查询和向量检索都必须隔离。
- 对工具定义细粒度 allowlist；模型不拥有 `execute_sql`、跨账户访问、绕过订阅或修改奖励规则的权限。
- 外部图片、语音转录、用户自由文本可能包含恶意指令；均视为不可信输入，不能提升权限。
- 疲劳与健康问题遵守证据、隐私与健康安全边界；缺少数据或不同步应说明。
- 模型供应商可替换（LLM Gateway）；领域能力协议与 AI 供应商解耦。
- 在 AI 对话/语音/照片记录中标注数据来源和授权范围，敏感数据最小化传输。

## 11. 典型 E2E 测试矩阵

1. 连点两次「开始训练」，仅一个 active session；两台设备并发也仅一个。
2. 客户端请求已经落库但响应丢失，查询状态返回已成功，不二次执行。
3. 同一幂等键配不同 payload，拒绝重用。
4. 两个用户/设备同时改同一计划，一个提交后另一个得到版本冲突并刷新。
5. 周五已经有训练，改期必须展示冲突，不能覆盖。
6. 已完成训练不能因改期被挪走；成长统计不重复增加。
7. 「周五改练背」单次修改不污染之后每个周五。
8. 生成新计划未确认、AI 崩溃或切换对话，不得替换当前计划。
9. 新计划确认成功但 Outbox 发布延迟，权威日历正确，提醒/洞察最终收敛。
10. 事件重复和乱序，通知/周报/徽章不重复触发。
11. 重复饮食保存不得产生两餐；两次真实独立进食仍可分别记录。
12. 同日两次真正称重允许存在；HealthKit 同一样本重复同步不产生重复记录。
13. 「有点累」只产生建议，不写日程；若用户明确请求休息，进入预览。
14. 离线训练记录、强杀恢复、重连后不丢组数。
15. AI API 故障时训练、饮食、体重原生操作仍可用。
16. 用户切换账号时不会看到上一账号的卡片、记忆或草稿。
17. 确认提案过期、数据变更、重复确认、取消后再次确认均有正确状态。
18. 奖励条件基于完成事实，修改计划/反复结束训练不会重复发奖。

## 12. 开发优先级（建议分阶段验收）

**Phase 0 审计**：读取现有全部相关业务代码、模型和数据库迁移；绘出训练计划/日历/会话/记录/HealthKit/Club 的真实写路径，列出现有不一致风险、自动化测试基线和回滚方案。

**Phase 1 统一 Domain Commands**：先收敛训练开始/结束、体重、饮食及计划修改的权威写入口，建设版本、幂等、审计；先不用 AI 自动操作，确保人工入口也共用新服务。

**Phase 2 Action Registry + AI Tool Router**：优先开放只读工具、开始/结束训练、创建饮食草稿、体重记录；结构化回复映射原生卡片。

**Phase 3 Proposal/Commit**：完成日程改期、单次替换、计划版本启用的预览/确认/冲突处理；对已完成训练做严格保护。

**Phase 4 Outbox + Sync**：保证事件可靠投递和投影去重，完成前后端状态恢复、离线同步、对账修复。

**Phase 5 长期个人智能**：对执行成功的动作生成洞察与记忆，加入反馈学习、主动但不打扰的提醒策略。

每阶段必须交付：实际修改文件清单、DB 迁移、API 契约、自动化测试、真机验证证据、监控/回滚方案，以及未完成的风险清单。禁止未经审计先大规模重写或直接部署到生产环境。
