## 已确认的测试脚本/口径问题

- 大批 MODEL_UNAVAILABLE 请求尚未进入模型，实际报 KeyError('label')：旧 boji_client.py 的 coach_days 构造 upcoming 只有 date/exercises，漏了 adaptive_core.clean_upcoming 要求的 label。没有把这种失败算成供应商速度或可用性问题。
- 006 把空消息 API 的 200 当作数据泄露，又把该判断复用到空会话列表；实际接口对不存在或外号会话按设计返回空列表。隔离仍要检查内容及 App 草稿，不能只看 HTTP 状态。
- 013、031、130、137～139、148、150、172、175 等需要分离夹具/控制操作和被测动作；合法首笔保存、设备干扰、提案取消不等于模型越权。不能简单删除所有负面断言，应重新设置 B1/B2 并精确限定目标。
- 100 的 clear 请求因缺有效幂等标识 422，随后用最新 profile version 显式提交另一目标成功；这没有复现“旧设备旧 revision 覆盖新目标”。141 的两个 400 也没有真正进入 CAS 竞态。
- 129 全库统计 Weight outbox，得到其他合成用户累计 236 条，不能证明当前 message 重复保存。155 的计划请求缺必需资料且 equipment 类型错误，400 不能证明 MiniMax 长输出失败。
- 071 不能用保护中的整日 Schedule.Replace 冒充未完成组的局部单位编辑；若实际 App 没有安全局部入口，功能仍应 FAIL。175 不能把 None/404 当作草稿已放弃。169 的自然句不是精确 deterministic 口令。

新版测试包逐案写明这些差异，并保留原功能验收要求。尤其已保存饮食纠正、计划导入、局部单位编辑等端到端能力，若重跑发现没有实现，必须继续列为缺陷，不能借“脚本问题”判 PASS。
