# 需求优先级与版本节奏 v1（产品经理 · 2026-11-09）

> 回答一个问题：**接下来做什么、什么不做、先做什么。**
> 排序原则不是"哪个功能更炫"，是"哪个不修会让用户当场弃用"。

---

## 一、三段节奏

### 第一段 · 可用性重修（**当前唯一主线，不做别的**）

**理由**：用户实测的原话是"操作逻辑、数据、使用感受没跑通，很乱、不整体、不像成熟产品"。这句话里有三个病根——**逻辑乱、数据乱、感受差**。这三个都不是新功能缺失造成的，是**现有功能之间没对齐**。再加功能只会让"乱"更严重。所以第一段不接任何新需求，只把已有的东西理顺。

| # | 需求 | 场景 | 期望感受 | 验收方式 | 批次 |
|---|---|---|---|---|---|
| R1 | **数字口径统一** | 同一天，首页说 1420 kcal，日报说 0 kcal，周报日均和趋势页不一样 | "这个 App 说的是同一件事" | 口径表 §六 D1–D7 全过 | 甲-3 / 甲-4 |
| R2 | **术语统一** | "总容量/力量总容量/额外负重/负重训练量"混用 | "每个词只有一个意思" | 全库 grep 只剩一个叫法 | 甲-2 起 |
| R3 | **空值不是 0** | 没记饮食显示 `0 kcal`、没训练显示 `0` | "没数据就是没数据，它不骗我" | 12 处空态逐个截图核 | 甲-2 / 甲-3 |
| R4 | **每屏一主操作** | 首页有 4 个视觉焦点 | "我知道该按哪个" | 判据 P0-2 逐页核 | 甲-1 起 |
| R5 | **核心动作 ≤3 步** | 记一餐要点 5 下 | "不用找" | 真机录屏数点击 | 甲-4 复验 |
| R6 | **空状态有交代** | 12 处空态，有插图没按钮 | "它告诉我下一步" | 判据 P0-4 逐处核 | 甲-2 / 甲-3 / 甲-4 |
| R7 | **日报数据卡前置** | AI 长文在上，数据卡在下 | "先看事实，再看解读" | 截图核层级顺序 | 甲-4 |
| R8 | **文案扫黑话** | 周期/洞察/RIR/执行率 | "说人话" | 禁用词表 grep + 人工抽读 | 全批次 |
| R9 | **状态分可解释** | 看到 72 分不知道为什么 | "我知道这分怎么来的" | 点巨号能看分项 | 甲-1 |

### 第二段 · 上架（**第一段全绿之后才做**）

**理由**：上架是"让陌生人第一次打开"。陌生人不会给你第二次机会——**第一屏决定留存**。当前状态下上架，等于把"乱"直接推给市场。所以第二段不是"提审流程"，是**上架前最后一次全页面终审 + 修掉终审发现的所有 🔴**。

| # | 需求 | 验收 |
|---|---|---|
| S1 | 全 28 页终审（判据文档 §三）零 🔴 | 亮/暗/AX 三套截图 |
| S2 | 三条主旅程真机走通 | 录屏 |
| S3 | 三联动实测（动效+震动+音效） | 真机 + 静音开关 |
| S4 | 降级路径实测（减少动态/增强对比度/iOS 17） | 真机 |
| S5 | 首屏引导 ≤3 步，新用户不登录也能逛 | 真机 |
| S6 | 隐私与健康数据授权文案过法务 | 运营文案 + 文档管理 |
| S7 | 崩溃率/启动耗时对齐性能基线 | `docs/performance-baseline-20261109-b1/measurements.md` |

### 第三段 · 留存（**上架稳定后才排**）

**理由**：留存功能解决"用得久了不够爽"，但前提是"第一次用不弃用"。在第一段没做完前做留存，是在漏水的桶上加水。

| 优先级 | 需求 | 理由 |
|---|---|---|
| P1 | **提醒体系**：训练提醒、称重提醒、日报提醒（已有开关，需做成"到点能改时间"） | 健身 App 的留存基本盘 |
| P2 | **周报→计划联动**：读完周报一键调整下周计划 | 闭环，日报已经能改明天 |
| P3 | **连续记录的正反馈**：连续天数、里程碑庆祝（不用奖章换积分，用动效） | 和已有"三联动庆祝"复用 |
| P4 | **成长季/俱乐部的内容填充** | 现有骨架在，内容弱 |
| P5 | 小组件增强 | 桌面入口 |
| P6 | AI 对话历史检索 | 长尾 |

## 二、本轮明确**不做**的（防止范围蔓延）

| 不做 | 理由 |
|---|---|
| 新的训练计划算法 | 用户反馈的是"乱"不是"计划不够聪明"，算法再好，界面乱照样弃用 |
| 社交/好友/动态流 | 健身 App 早期社交是负担，且审核成本高 |
| 自绘控件 | 用户已明确要求原生组件，自绘会同时得罪用户和审核 |
| 新的首页模块 | 首页当前要做的不是加内容，是**减到只剩一个主角** |
| 深色模式新设计 | 深色是**降级路径**不是新功能，必须跟亮色一起过 |
| iPad 适配 | 现在先把 iPhone 做到极致 |

## 三、风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 第一段工程量被低估（口径统一牵动 6 处重算点） | 高 | 中 | 已拆到具体文件行号（口径表 §八），可分批做，先做 R3（空值）再 R1（对账） |
| 改口径时把历史数据算坏 | 中 | 高 | 口径改动只动**读出层**，不改存储；改动后跑 §六 D1–D7 对账 + 已有单测 |
| 施工期又加新需求 | 高 | 高 | 本文件即"本轮不做清单"，Chief 已有最终裁决权；新需求进第三段排队 |
| 用户醒来看到的东西仍然"不整体" | 中 | 极高 | 终审必须**双人**（Chief + 产品经理），且必须走真实旅程，不许只看图 |
| 真机走查发现系统级问题（性能/崩溃） | 低 | 高 | 第二段 S7 性能基线对齐 |

## 四、我需要 Chief 确认的三件事（不阻塞当前施工）

1. **第三段优先级排序**是否认可（我把"提醒体系"排在最前，因为它是健身 App 留存底盘）。
2. **口径表 §七 术语统一**会不会大面积改文案 → 如果影响运营文案工作量，需要提前给运营文案排期。
3. **终审时间窗**：建议在"全部批次编译绿 + 截图齐"之后、出 TestFlight 包之前做，理由是终审发现的 🔴 不该让用户装机后才看到。
