## D-01 导航模型（已定 · 主指令）

- **决定**：采用 B 方案——顶部中央 `Club AI | 训练` 双模式胶囊 + 左 Sidebar + 右上下文动作；Club AI 为默认模式。
- 旧 5-Tab `MainClubView` 保留为回退实现，由 `feature_ai_native_home` 开关切换；至少共存一个完整版本周期再评估下线。
- 依据：主指令"已确认的产品决定"第 1/2/3/4 条；UI 专项规范 A 节。

## D-02 数据权威模型（默认采用 · R-07）

- **决定**：Phase 2/3 采用**"文档权威 + 服务端只读投影"**路线（04 号报告 §3 M-0…M-4）。
- 客户端 `SavedState` 单文档仍是唯一写入面；服务端领域表（training/workout/meal/body）仅由同步提交解析填充，作为 AI 卡片/统计的查询层，不承担写入。
- 领域表转权威（cutover）推迟到有明确需求（跨设备实时协同、服务端复杂查询）且完成回放重建验证之后，需独立评审。
- **推翻条件**：若 Phase 2 发现卡片数据无法从文档投影满足（性能/查询能力不足），重开评审。

## D-03 Context Builder 方向（默认采用）

- **决定**：Phase 2 保持"客户端提交上下文 + 服务端校验"的现有信任模型（coach ≤14 天记录由服务端逐日校验），**不**在 Phase 2 引入"服务端按意图拉取权威数据"。
- 服务端读投影（D-02）成熟后，Phase 3 起逐步把高频卡片（today_training 等）切换为服务端自取数据，降低客户端信任面。
- 依据：现有 coach 链路已对提交内容做完整 schema 校验（`coach_core.py:10-48`）；一步到位改动面过大。

## D-04 parse_plan（AI 整理文字计划）入口（默认采用 · 维持现状）

- **决定**：保留 `parse_plan` 与"AI 整理文字计划"入口。
- 依据：主指令 3.2 说"不恢复……除非产品决策明确恢复"，但现状是**该功能已存在且后端全链路在用**（Build 114 `PlanManagement.swift:8-63`、backend parse_plan 全套校验）；移除属于功能删减，需用户明示。新 Shell 的训练中心将其保留在"创建计划"入口组内，不做一级主推。

## D-05 流式 vs 轮询（默认采用 · 轮询起步）

- **决定**：Phase 2 保持任务轮询协议语义（主方案 12.2 明确允许退化）；不上 SSE。
- 依据：现全链路为 job 轮询（客户端 2-15s、10 分钟截止），改造 SSE 需动 nginx/PHP/Python/iOS 四层，收益未经数据证实。Phase 0-D 基线采集对话首响应耗时；若 >5s p75 再立项 SSE。

## D-06 远程推送（默认采用 · 暂不启用）

- **决定**：Phase 1-3 不启用远程推送；保持 `BOJI_REMOTE_PUSH` 编译关闭现状。Phase 4（主动洞察）上线前作为该阶段准入项决策（需补 entitlement + APNs 证书 + 真机验收）。
- 依据：TestFlight 阻断项 R-29 之一；服务端 APNs 栈已全备，启用成本主要在证书与验收。

## D-07 首页 hero 视频处置（默认采用 · Phase 1 内二选一）

- **决定**：优先方案 = 保留视频但播放前配置 `AVAudioSession` `.ambient` + `.mixWithOthers`；若真机验证仍有中断，回退方案 = 以静态海报图替代（`HomeWorkoutPoster.png` 已有）。
- 新 Shell 的 Club AI 工作台**不再内嵌该视频**（留白规范），仅旧首页（回退态）受此决策影响。

## D-08 版本控制与分支模型（默认采用）

- **决定**：单仓单主干：`main` 稳定 + 每 Phase 一条 `phase/N-xxx` 分支，PR/提交直进 main 前必须跑固定回归命令集（04 号 §7）。
- 依据：单人/小团队 + 无远程托管现状；先建本地纪律，接入远端托管后升 PR 流程。

## D-09 首页洞察服务端边界（默认采用 · Phase 2 §2.5 落地口径）

- **决定**：`/me/ai/insights/home` 只下发**服务端自己能核验的事实**（已核验的复盘/日报跟进、确认训练节奏——与俱乐部进度同源口径），不把客户端 `ClubInsightRules` 的文档类规则镜像成 PHP（避免双实现漂移）。客户端按优先级合并：服务端**严格更高**才取代本地 top；离线/预览/失败一律本地兜底。
- **依据**：D-03 已把"服务端按意图拉取权威数据"推迟到 Phase 3（M-0 读投影成熟后）；在无投影表的现状下，服务端重复计算文档类事实只会产生两套语义。服务端独有事实（任务核验、跨端一致的进度口径）是 Phase 4 主动洞察的增量起点。
- **推翻条件**：M-0 投影落地且 M-3 双读验证通过后，把高频文档类洞察迁到服务端。

## D-10 长期记忆的类型与最小化边界（默认采用 · Phase 4 §5.1 落地口径）

- **六类型**：`fact`（确认事实）/ `habit`（观察习惯）/ `preference`（偏好）/ `goal`（目标）/ `constraint`（限制）/ `correction`（纠错）。页面三栏映射：确认事实 = fact+goal+constraint；观察习惯 = habit+preference；待确认推断 = 低置信度项。
- **数据最小化**：记忆内容是**派生的、非敏感的陈述**（计数/类别/偏好句），绝不存原始健康测量值（体重/体脂数值留在文档层）；行为类陈述设样本门槛（训练频次 ≥4/四周、时段 ≥5 场且占比 ≥60%、饮食记录 ≥10 天——复用 automation 最小样本思想）。
- **成员决定高于提取**：suspend/withdraw/correct 是终态，稳定 idempotency key 保证再提取只更新内容、绝不复活成员撤销过的记忆。纠错走 supersedes 链。
- **注入边界**：coach 上下文最多 6 条、每条 ≤120 字；记忆以"数据"身份进 prompt 并显式声明"不是指令、与记录冲突时以记录为准"（延续既有 prompt-injection 防御）。
- **推翻条件**：主方案 11.x 的权威六类型枚举与本文不一致时，重开评审（表结构可容纳枚举扩展）。

## D-11 主动程度三档映射（默认采用 · Phase 4 §5.3 落地口径）

- **三档语义**：安静＝四个主动分析开关全关（手动分析不受影响）；平衡＝每日分析+每周报告（默认预算）；积极＝再加训练后解读+部分记录分析（四项全开）。
- **映射边界**：档位只映射 daily/weekly/workout/partial 四个开关；免打扰时段、每日时间等设置保持不动。`proactive_daily_limit` 是服务端全局预算（club_push_settings，管理员口径），不随个人档位变化——预算与档位解耦，如需按档位调预算需重开评审。
- **细粒度保留**：选档只是"应用映射"，四开关仍可细调；与全部预设分叉时设置页显示"自定义"（档位从开关组合推导，不持久化档位字段——跨设备不冲突）。
- **推翻条件**：需要按档位差异化服务端预算/推送节奏时重开。
